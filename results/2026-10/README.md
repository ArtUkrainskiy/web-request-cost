# Results — bare runtimes with their defaults, 16–17 October 2026

The 12 implementations of [implementations/](../../implementations), each as its vendors ship it ([docs/rules.md](../../docs/rules.md)), on one machine. `tables.md` is generated by `aggregate.py` from `data/raw/` and `prices.json`; every published number comes from there.

## Environment
- AMD Ryzen 9 5950X (16 cores / 32 threads, two CCDs), 62 GB RAM; Ubuntu 26.04, kernel 7.0, governor `performance`, boost on; Docker 29 with the host network.
- CPU sets: databases 0–5,16–21 (12 threads); load generator 6–7,22–23; stack 8–11,24–27 (4 cores / 8 threads, N = 8); upstream stub 12–15,28–31. Everything talks over loopback.
- PostgreSQL 17.11 (`ssl=off`) and MySQL 8.4.11 (official images, `max_connections` 300), PgBouncer 1.25.1, nginx 1.30.5, wrk 4.1.0, wrk2 (commit 44a94c1). Runtime versions: [implementations/README.md](../../implementations/README.md).
- Checked on the host, not part of the records: the PHP builds carry the compiler and linker flags of the official PHP image (`-fstack-protector-strong -fpic -fpie -O2 -D_LARGEFILE_SOURCE -D_FILE_OFFSET_BITS=64`, `-Wl,-O1 -pie`), and the C part of FrankenPHP the same compiler flags, as in FrankenPHP's official Dockerfile (`go version -m` shows them in the binary).
- Paths under the home directory of the measuring host are written as `~` in the data files.

## Data
| file | content |
|---|---|
| `data/raw/memory-*` | equal numbers of clients: 12 stacks × 2 databases × C = 1, 10, 50, 200 × 3 passes in shuffled order |
| `data/raw/rate-*` | fixed request rates: 12 stacks × 2 databases × 1000, 2000, 4000 req/s over 48 connections (wrk2 `-c50` over 4 threads) × 3 passes in shuffled order |
| `data/raw/memory-ruby-*`, `data/raw/rate-ruby-*` | Ruby in both series with 3 Puma threads per worker, one per database connection; the Ruby runs in `memory-2026…` and `rate-2026…` used Puma's default of 5 threads, with two threads per worker waiting for a connection, and are kept for comparison only (section 1b of the tables) |
| `manifest.txt` | sha256 of the measured binaries and lock files, runtime versions, image IDs |
| `data/raw/check-*` | checks of section 1b: .NET with the rates in ascending and in descending order on one start, and with the thread pool's spinning switched off (one pass each); section 1b also compares the Ruby runs with 5 and 3 threads |
| `data/raw/variant-fpm-*` | PHP-FPM on PostgreSQL, C = 50, 3 passes each: emulated prepares; `Pdo\Pgsql::ATTR_DISABLE_PREPARES`; native prepares through PgBouncer |
| `data/raw/wait100-*` | waiting series (PostgreSQL), 100 ms × 100 clients, 3 passes |
| `data/raw/wait1000-*` | waiting series (PostgreSQL), 1 s × 100 / 1000 (RoadRunner 500) / 5000 (event-loop and virtual-thread stacks) clients, 3 passes |

Each `.log` next to a `.jsonl` lists every sweep and whether it was accepted; nothing was removed from the files. 700 runs: 649 in the four series, 42 of Ruby with 3 threads, 9 checks. Two sweeps were rejected and rerun at the end of their series: Swoole on PostgreSQL did not reach 95% of 4000 req/s (3426 and 3794 req/s); the runs of those sweeps at 1000 and 2000 req/s stay in the file, so Swoole on PostgreSQL has 5 runs at those rates.

## Record fields
One JSON object per run:
- run settings: `stack`, `db`, `c` (wrk connections), `rate` (req/s in the fixed-rate series, `null` otherwise), `duration` and `warmup` (s), `pause` (s between warm-up and measurement), `containers`, `stack_cpus`, `container_cpus`, `load_cpus`, `host`, `time`, `governor` (scaling governor / energy preference / boost), `php_workers`, `stmt_cache`, `upstream`, `via_bouncer`, `pdo_emulate`, `env` (Go environment and the variant options `PHP_INI_EXTRA`, `POOL`, `SWOOLE_POOL`, `DSN_SUFFIX`, `PHP_ZTS_BUILD`, see [harness/README.md](../../harness/README.md)) — the variables as given to the harness, empty (`php_workers`: `default`) when the stack's default applies;
- `config`: the effective configuration — command, environment and image ID of every container of the stack, and the configuration files `up.sh` wrote (php.ini, FPM pool, nginx, Caddyfile, rr.yaml, PgBouncer);
- `dbinfo`: versions and settings of both databases (`db.sh check`); `db_tls_sessions`: TLS sessions to MySQL at the end of the run (0 in every run);
- `wrk`: `requests`, `duration_us`, latency percentiles `p50_us` / `p90_us` / `p99_us` / `max_us`, status counts `s200` / `s401` / `s404` / `s5xx` / `sother`, `non2xx`, `errors` (connect, read, write and timeout errors), `body_bytes`;
- `cpu_window`: cgroup CPU seconds of the stack and of each database between snapshots taken right before and right after wrk, and the wall time between them (`seconds`) — CPU per request is `cpu_window.stack / wrk.requests`;
- `sample` (cgroup sampler, every 200 ms): per container group (`stack`, `blog-pg`, `blog-mysql`) `mem_median` / `mem_max` (bytes of `memory.current`), `mem_stat_at_max` (anon, file, kernel, sock, shmem from `memory.stat` at the peak, bytes), `mem_peak_since_start` (`memory.peak`), `cpu_s` (CPU seconds over the sampler's window, which starts before and ends after wrk);
- `cpu_busy`: busy threads of each CPU group of the host during the window (`stack`, `load`, `db`, `upstream`, `other`).

## Reading the tables
- Sections 1, 1a, 1b, 2, 3 and 6 are measured. Sections 4, 5 and 8 are a model built on them (see their headers); nothing ran on an 8-vCPU server.
- Database CPU per request follows the driver's default: statements cached per connection (pgx, PgJDBC, asyncpg) cost PostgreSQL 0.52–0.58 ms per request at 2000 req/s, statements parsed every time 1.23–1.50 ms (section 1a); at 50 clients, where the database is saturated, 0.78–0.82 against 1.75–2.02 ms (section 1). What each driver does on the wire is in [docs/rules.md](../../docs/rules.md).
- The waiting series provisions the blocking models for the load (a PHP worker or about two Puma threads per concurrent request); it shows what each model needs for C waiting requests without a queue, not how a fixed pool behaves under that load.
- In the waiting series FPM, FrankenPHP and RoadRunner reach PostgreSQL directly with 100 workers and through PgBouncer with 500 (RoadRunner) or 1000 workers, which do not fit into 300 server connections. PgBouncer keeps their prepared statements on its server connections, so their database CPU there (about 0.72 ms per request, against 1.5–1.75 ms directly at 100 workers) is that of a cached statement, while PHP and PgBouncer pay the prepare and close exchanges on the stack's side; section 6 shows the same trade-off without waiting.
