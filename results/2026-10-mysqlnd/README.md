# mysqlnd statistics in ZTS builds: FrankenPHP + MySQL, 19 October 2026

A follow-up series to [results/2026-10](../2026-10): what mysqlnd's client statistics cost the FrankenPHP stack on MySQL, and what they cost with atomic counters instead of a mutex. Tables: [tables.md](tables.md), generated by [aggregate.py](aggregate.py) from [data/raw/](data/raw).

## Why

In thread-safe (ZTS) PHP builds, every update of mysqlnd's statistics takes a mutex ([`ext/mysqlnd/mysqlnd_statistics.h`](https://github.com/php/php-src/blob/1c9242e7fecbaff646b677b46cf9962831fc2fa2/ext/mysqlnd/mysqlnd_statistics.h#L19-L32)). The global statistics are one object per process, so all PHP threads take the same mutex on every counted packet and row. Statistics are on by default (`mysqlnd.collect_statistics=1`). FrankenPHP runs the ZTS build (`.build/php85-zts`); FPM, RoadRunner and Swoole run the NTS build, where the lock macros are empty. The FrankenPHP rows on MySQL in results/2026-10 run with statistics on.

## Variants

| variant | build | php.ini |
|---|---|---|
| `stats-on` | `.build/php85-zts`, the build of results/2026-10 | as published (statistics on, the default) |
| `stats-off` | the same | plus `mysqlnd.collect_statistics=0` (`PHP_INI_EXTRA`) |
| `atomic-on` | `.build/php85-zts-atomic`: the same sources with [mysqlnd-atomic-php-8.5.11.patch](mysqlnd-atomic-php-8.5.11.patch), reconfigured and rebuilt (`PHP_ZTS_BUILD`) | as published (statistics on) |

The patch replaces the locked increment with a relaxed atomic addition under ZTS (`__atomic_fetch_add(..., __ATOMIC_RELAXED)`); NTS builds are unchanged. It is a prototype for this measurement, not the change proposed to php-src.

## How it ran

- The harness of this repository at the commit of results/2026-10 (`afd7ea6`), unchanged, on the same machine and CPU sets: FrankenPHP 1.13.1 worker mode with 16 workers on CPUs 8–11 and 24–27, MySQL 8.4.11 on 0–5 and 16–21, the load generator on 6–7 and 22–23; governor `performance`, boost on (recorded in every record).
- [run.sh](run.sh) runs 3 passes. In each pass the three variants run one after another (reversed on even passes), each on a fresh start of the stack with the response check: first the 50-client closed-loop settings of the memory series (warm-up 3 s, 10 s measured), then the fixed rates of section 1a (1000 / 2000 / 4000 req/s over 48 connections, warm-up 15 s, 20 s measured). The run used the same script with absolute paths; paths in the records are relative to the repository.

## Results

Stack CPU per request (the FrankenPHP container), median of 3 passes; the change is the median of the per-pass ratios to `stats-off`:

| load | statistics on | statistics off | on, atomic counters | on against off | atomic against off |
|---|---:|---:|---:|---:|---:|
| 1000 req/s | 0.342 ms | 0.317 ms | 0.322 ms | +7.2% | +1.6% |
| 2000 req/s | 0.327 ms | 0.298 ms | 0.301 ms | +9.4% | +0.8% |
| 4000 req/s | 0.327 ms | 0.277 ms | 0.282 ms | +17.7% | +1.9% |
| 50 clients, database saturated | 0.411 ms | 0.312 ms | 0.318 ms | +32.2% | +2.8% |

The cost of the statistics grows with the request rate; with atomic counters it is 0.8–2.8% above statistics off at every load. The database's CPU per request is the same for the three variants (tables.md).

The same configuration as `stats-on` in results/2026-10: 0.332 ms at 2000 req/s and 0.405 ms at 50 clients, against 0.327 and 0.411 ms here.

A first run of this series on the same day ran with the `powersave` governor after a reboot of the machine and is not used; the script now refuses to start on any other governor than the published one.
